A map of every BEThoven entity — in memory, on disk, or never stored at all — and where each should live once persistence lands. The answer is two new tables. Everything else stays exactly as durable, or as disposable, as it already is.

00How to read the map

Four ways a thing can exist

Color is the argument. A thing's durability decides its treatment — solid and warm if it survives a restart and a backup, cool and dashed if it evaporates, a ghost outline if it was never really there to begin with.

Persisted — domain DB
In the vault. Single-writer SQLite, covered by the .backup rule. Non-reproducible, or the auth credential itself.
Append-only log
On disk, greppable, unbounded by design. A forensic trail an operator tails — never read by the app, never state.
Volatile — in memory
Gone on restart, on purpose. Re-fetched from the feed or regenerated by a worker within one interval.
Derived — recomputed
Never stored. A pure fold of the durable inputs, recomputed on every read so a corrected result re-flows for free.

02The two that matter

Decision records

Scoring and BETanIA were the contested ground. Both resolved the same way: the durable thing earns a row; the derivable thing does not, no matter how convenient a cache would feel.

DEC · 01

Scoring & standings

Persist nothing derived. Keep recompute-on-read for the whole board. Add one append-only audit log of result writes — and nothing more.

-- the only new scoring table: input history, never output CREATE TABLE IF NOT EXISTS result_events ( id INTEGER PRIMARY KEY AUTOINCREMENT, match_id INTEGER NOT NULL REFERENCES matches(id), score_a INTEGER NOT NULL, score_b INTEGER NOT NULL, source TEXT NOT NULL, -- 'admin' | 'feed' actor_fp TEXT, -- admin fingerprint; NULL for feed created_at TEXT NOT NULL -- RFC3339 UTC, from clock.Now() );

Why this, and only this

Every score on the board is a pure function of (bets, results, mode). That's what makes "edit a result, or flip the mode, and everything re-derives" free — the property worth protecting above all.

The one real hole: a result write destructively overwrites matches.score_a/b with zero trace of the prior value, the actor, or whether it came from an admin or the feed. result_events records the input, never the output — so it can never drift from scoring.Score, and it costs one INSERT on a path that fires a few hundred times across an entire World Cup.

Rejected

Points ledger and per-round standings snapshots. Both store output, so both rot the instant scoring_mode flips (Classic → Proximity rescales every historical point) or a late Scarcity bet lands (pool-relative — one bet shifts everyone on that match).

They'd trade today's zero invalidation points for five: PlaceBet, EnterResult, FinalizeFromFeed, seed-Upsert, and SetScoringMode. A missed one is a silent wrong-scoreboard bug.

In-memory memo of the settled base: deferred, not built — correct as an eventual perf lever, theoretical at friend-pool scale.

⚔ Strongest objection · and the rebuttal

"You're adding schema and a txn refactor to fix a hole that never bit a hobby pool — analytics already logs result entries. You broke your own 'persist nothing' instinct for a forensic nicety."

Rebuttal: the result write is the single least-reversible mutation in the system — it re-derives every standing for the rest of the tournament, and today it's overwritten with no in-domain record at all. The supposed coverage doesn't hold: analytics is off by default, in a separate lossy DB explicitly excluded from the backup rule. The ledger stores an input, not derived state — the one category that genuinely earns a row — so it adds zero invalidation surface. The "persist nothing" instinct was right for derived state, and it's kept absolutely.

DEC · 02

BETanIA — the AI player

Persist exactly one new thing: the model's rationale, keyed 1:1 to the bet. Comments, narratives, and worker counters stay volatile. Logs stay the audit trail.

-- sibling to the bet, not a column on it CREATE TABLE IF NOT EXISTS ai_prediction ( bet_id INTEGER PRIMARY KEY REFERENCES bets(id) ON DELETE CASCADE, source TEXT NOT NULL DEFAULT '', -- 'seed' | 'live' rationale TEXT NOT NULL DEFAULT '', -- ai.sanitizeText'd before write confidence TEXT NOT NULL DEFAULT '', created_at TEXT NOT NULL );

Why this, and only this

The pick already persists — it's a bet, re-priced by AIBets across restarts. Comments are a pure fold of finished matches via StandingsHistory; caching them would let a stale roast outlive a corrected result.

The one thing neither stored nor derivable is the model's free-text reasoning — external Claude output you'd otherwise re-pay for or lose. Today it lives only in the volatile 50-entry ring (the documented "Recent picks: nothing yet" gap) and a grep-only log. A sibling row keyed to the bet closes that permanently, and AIBets already loads exactly the rows to join against.

Sibling, not ALTER bets: keeps untrusted model text out of the hot, heavily-tested scoring source row. Read only on the admin's gated session. The ai package never learns the table exists — the service writes it after the bet, preserving ai-never-imports-service.

Rejected

ALTER bets with AI columns — pollutes the most-tested table with fields empty for every human bet, and puts model text inside the scoring fold's source row.

ai_runs — worker counters are per-process by design; a 6h write-per-pass onto the single writer buys forensics that belong in analytics.db if anywhere.

ai_comments / ai_narratives tables — caching a pure derivation. The TTL + grace cache is the correct decay story; the log is the history.

⚔ Strongest objection · and the rebuttal

"Cosmetic. The rationale already lives in ai_bets.log — tail it. Net-new schema and a write path on a one-VM hobby pool for a column that's blank for one interval."

Rebuttal: rationale is the one datum genuinely not derivable — external API output, not a fold of stored data — so the test that correctly kills ai_comments points the other way here. The log is an append-only tail, not a query surface; the admin panel was explicitly built around DB-sourced picks "so they survive a restart." The rationale is the lone column of that panel still living only in the volatile ring. This finishes a fix the codebase already committed to.

03The honest part

Where the agents disagreed

The inventory pass wanted to persist far more. The synthesis pass — adversarially checked — trimmed nearly all of it. The split is itself the useful artifact.

The expansive view

optimizes for: admin observability surviving a restart

  • A whole separate ai.db — ai_picks, ai_actions, ai_comments
  • Persist the CommentCache behind a write seam, hydrate on boot
  • A standings_snapshots table — an "as-shown" archive per round
  • Persist live.Cache as a write-behind shadow

The trimmed view (adopted)

refuses to: cache any pure derivation

  • Two tables, both in the domain DB: result_events, ai_prediction
  • Comments stay volatile — the cache + log already answer "what does she say now" and "what has she ever said"
  • No snapshots — StandingsHistory re-derives, and a snapshot lies the moment a result is edited
  • No live.Cache shadow — the feed re-populates in < 60s, and a stale row fabricates phantom points

Resolution leans trimmed: every rejected table caches a fold of data the system already holds, and each one buys an invalidation burden the system currently has zero of. The expansive view's one fair point — admin telemetry blanks for ~6h after a restart — is a cosmetic gap on an admin-only panel, not a correctness hole.

+ Cheap additive wins both passes liked

Analytics indexes — idx_events_name_at and idx_events_user_name_at so the admin rollups stay index-only as the event log grows. Pure CREATE INDEX IF NOT EXISTS, applied on boot.

team_forms (optional) — persist only the pre-tournament form baseline, so admin corrections survive restart and form decouples from the placeholder fixtures.json. The computed strip stays derived.

04Before any of it ships

Open questions

?
Backfill result_events from existing match scores on first deploy, or start history at the migration? → Recommend: start at migration; the projection stays authoritative.
?
Wrap SetResult / SetResultIfUnfinished in a txn at the store, or compose append + update at the service layer? → Decides whether the store grows a txn API.
?
Wire SavePrediction into the seed too, or accept that backfilled past-game rationale stays log-only? → Cheap to include; the panel mostly cares about live reasoning.
?
Keep confidence as opaque TEXT, or normalize to an enum at the sanitize boundary so the panel can sort by it later?
?
Does the result audit need a gated admin TUI screen for launch, or is a DB-query artifact enough at first?
