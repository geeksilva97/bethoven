# Persistence design — every entity, mapped

> **Status:** design / not implemented. A map to react to, not committed code.
> **Scope:** every BEThoven entity — in memory, on disk, or never stored — and
> where each should live once persistence lands.
> **Emphasis:** scoring and BETanIA (the contested ground).
> **Provenance:** 20-agent analysis (6 inventory → 6 design → 6-lens trade-off
> panel → 2 adversarially-checked syntheses).
> A visual version lives next to this file: [`persistence-map.html`](./persistence-map.html).

## Thesis

**Persist the inputs. Recompute the rest.** The recommendation is deliberately
small — **two new tables** — because the codebase's existing discipline (pure
scoring, volatile caches, a separate analytics DB) is already most of the right
answer.

## How to read the storage classes

| Class | Meaning |
|---|---|
| **Persisted — domain DB** | In the vault. Single-writer SQLite, covered by the `.backup` rule. Non-reproducible, or the auth credential itself. |
| **Append-only log** | On disk under `ReadWritePaths`, greppable, unbounded by design. Operator forensics — never read by the app, never state. |
| **Volatile — in memory** | Gone on restart, on purpose. Re-fetched from the feed or regenerated by a worker within one interval. |
| **Derived — recomputed** | Never stored. A pure fold of the durable inputs, recomputed on every read so a corrected result re-flows for free. |

## The two new tables

Both land in the **domain DB**. Nothing else changes there.

### `result_events` — result-write audit (scoring)

```sql
-- the only new scoring table: input history, never output
CREATE TABLE IF NOT EXISTS result_events (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  match_id      INTEGER NOT NULL REFERENCES matches(id),
  score_a       INTEGER NOT NULL,
  score_b       INTEGER NOT NULL,
  source        TEXT NOT NULL,   -- 'admin' (EnterResult) | 'feed' (FinalizeFromFeed)
  actor_fp      TEXT,            -- admin fingerprint; NULL for feed
  created_at    TEXT NOT NULL    -- RFC3339 UTC, from clock.Now() (never time.Now())
);
```

Today `EnterResult` → `store.SetResult` and `FinalizeFromFeed` →
`store.SetResultIfUnfinished` are single statements that **destructively
overwrite** `matches.score_a/score_b` with zero history — and that write silently
re-derives the entire leaderboard and `StandingsHistory` for the rest of the
tournament. This logs the **input** (score + who + when + source), never the
output, so it can never drift from `scoring.Score`. One INSERT on a path that
fires a few hundred times across an entire World Cup, wrapped in the same
single-writer txn as the projection update.

### `ai_prediction` — BETanIA's reasoning (AI)

```sql
-- sibling to the bet, not a column on it
CREATE TABLE IF NOT EXISTS ai_prediction (
  bet_id     INTEGER PRIMARY KEY REFERENCES bets(id) ON DELETE CASCADE,
  source     TEXT NOT NULL DEFAULT '',   -- 'seed' | 'live'
  rationale  TEXT NOT NULL DEFAULT '',   -- ai.sanitizeText'd before write
  confidence TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL
);
```

The pick already persists (it's a `bet`, re-priced by `service.AIBets` across
restarts). The model's free-text **reasoning** is the one datum that's neither
stored nor derivable — external Claude output that today lives only in the
volatile 50-entry ring (the documented *"Recent picks: nothing yet"* gap) and a
grep-only log. A sibling row keyed to the bet closes that permanently;
`AIBets` already loads exactly the rows to join against.

**Sibling, not `ALTER bets`** — keeps untrusted model text out of the hot,
heavily-tested scoring source row, and the row is read only on the admin's gated
session. The write is initiated by the **service** (after `PlaceBet` succeeds)
and the **seed CLI** (after `UpsertBet`); the `ai` package never learns the table
exists, preserving the `ai`-never-imports-`service` rule. Because `store.UpsertBet`
returns only `error` and `bets` has `UNIQUE(user_id, match_id)`, a
`SavePrediction(userID, matchID, …)` store method resolves `bet_id` via sub-SELECT
and upserts — no new bet-id plumbing.

## Full entity inventory

### Domain DB — already persisted (no change)

| Entity | Decision | Note |
|---|---|---|
| `tournaments` | persist | one active row, FK root |
| `users` | persist | fingerprint = identity, immutable |
| `matches` | persist | `Live*` overlaid at read, never columns |
| `bets` | persist | the one non-reproducible scoreline; BETanIA's picks live here too |
| `settings` (KV) | persist | `public_bets`, `scoring_mode`, `comment_tone`, per-user tone/hide, `comment_context` |
| **`result_events`** | **persist (NEW)** | result-write audit — input history |
| **`ai_prediction`** | **persist (NEW)** | BETanIA's rationale, 1:1 with the bet |

### Separate DB — `analytics.db` (own connection, losable, opt-in)

| Entity | Decision | Note |
|---|---|---|
| `events` | persist | already there; **+ `idx_events_name_at`, `idx_events_user_name_at`** for rollups |
| event `props` | persist | stays JSON — schema never churns per new event type |
| analytics connection / buffer / drop counter | volatile | process-scoped; async fire-and-forget must never backpressure a bet |
| Overview / PlayerStat / Bucket | derived | `COUNT`/`GROUP BY` on demand, now index-backed |

### Volatile — in memory (re-fills within one interval)

| Entity | Decision | Note |
|---|---|---|
| `live.Cache` / `live.Score` | volatile | feed re-populates < 60s; a persisted stale score fabricates phantom points |
| `live.Event` | volatile | per-request transient, untrusted pre-resolution feed data |
| `ai.Monitor` (counters + 50-action ring) | volatile | per-process; lifetime totals derivable from logs if ever wanted |
| `ai.CommentCache` | volatile | TTL + grace; caching a derivation would outlive corrected results |
| `ai.CommentMonitor` | volatile | per-process telemetry |
| `ai.Bettor` / `live.Poller` | volatile | goroutines, not data; seams re-wired at boot |

### Append-only logs (operator forensics)

| Entity | Decision | Note |
|---|---|---|
| `ai_bets.log` | log | JSON line per pick (seed + live) |
| `ai_comments.log` | log | JSON line per comment; full history vs. the table's "current set" |

### Derived — recomputed every read (pure fold)

| Entity | Decision | Note |
|---|---|---|
| Pure scoring fns / `scorer` / `scoring.Pool` | derived | persisting output couples DB to tunable constants |
| `Standing` / Leaderboard / `LiveRankDelta` | derived | live-folded total must never be frozen as settled |
| Live provisional-points fold | derived | **forbidden** to persist — central live-feed safety property |
| `MatchResult` / `MatchStanding` / `Breakdown` | derived | recomputed only after a result exists (blind-bet boundary) |
| `StandingsHistory` | derived | pure fold of finished matches; edit re-derives |
| `betterRank` | derived | stateless ordering predicate (single source of truth) |
| `Narrative` / `CommentConfig` / `Rivalry` | derived | transient intermediate / projection of persisted settings |
| `FinalizeFromFeed` result write-back | persist | already the one sanctioned transient→durable boundary (`!Finished` guard) |

## Decision 01 — Scoring & standings

**Persist nothing derived.** Keep recompute-on-read for the whole board. Add
**one** append-only audit log of result writes (`result_events` above) — and
nothing more.

**Why.** Every score is a pure function of `(bets, results, mode)`. That's what
makes "edit a result, or flip the mode, and everything re-derives" free — the
property worth protecting above all. The only real hole is the destructive,
trace-less result overwrite, which `result_events` closes by recording the input.

**Rejected:**

- **Points ledger** and **per-round standings snapshots.** Both store *output*,
  so both rot the instant `scoring_mode` flips (Classic → Proximity rescales every
  historical point) or a late Scarcity bet lands (pool-relative — one bet shifts
  everyone on that match). They'd trade today's **zero** invalidation points for
  five (PlaceBet, EnterResult, FinalizeFromFeed, seed-Upsert, SetScoringMode); a
  missed one is a silent wrong-scoreboard bug.
- **In-memory memo** of the settled base: deferred, not built — a correct eventual
  perf lever, but theoretical at friend-pool scale and it adds a dirty-version
  invariant every writer must bump.

**Strongest objection → rebuttal.** *"Adding schema to fix a hole that never bit a
hobby pool; analytics already logs result entries."* — The result write is the
least-reversible mutation in the system and is overwritten with no in-domain
record. Analytics is off by default, in a separate lossy DB excluded from the
backup rule, so it can't be relied on. The ledger stores an **input**, not derived
state — the one category that earns a row — so it adds zero invalidation surface.

## Decision 02 — BETanIA (the AI player)

**Persist exactly one new thing:** the model's rationale/confidence, keyed 1:1 to
the bet (`ai_prediction` above). Comments, narratives, and worker counters stay
volatile. Logs stay the audit trail.

**Why.** The pick already persists and re-prices across restarts. Comments are a
pure fold of finished matches; caching them lets a stale roast outlive a corrected
result. The rationale is the lone non-derivable datum and the lone column of the
admin panel still living only in the volatile ring.

**Rejected:** `ALTER bets` (pollutes the hot scoring source row with model text);
`ai_runs` (per-process counters belong in `analytics.db` if anywhere);
`ai_comments` / `ai_narratives` tables (caching a pure derivation).

**Strongest objection → rebuttal.** *"Cosmetic — tail `ai_bets.log`."* — Rationale
is the one datum genuinely not derivable (external API output), so the test that
kills `ai_comments` points the other way here. The log is a tail, not a query
surface; the panel was explicitly built around DB-sourced picks "so they survive a
restart." This finishes a fix the codebase already committed to.

## Where the agents disagreed

The inventory pass wanted to persist far more; the synthesis pass — adversarially
checked — trimmed nearly all of it.

| The expansive view (rejected) | The trimmed view (adopted) |
|---|---|
| A separate `ai.db`: `ai_picks`, `ai_actions`, `ai_comments` | Two tables, both in the domain DB |
| Persist the `CommentCache` behind a write seam, hydrate on boot | Comments stay volatile — cache + log already cover "now" and "ever" |
| A `standings_snapshots` "as-shown" archive per round | No snapshots — `StandingsHistory` re-derives; a snapshot lies once a result is edited |
| Persist `live.Cache` as a write-behind shadow | No shadow — feed re-populates < 60s; a stale row fabricates phantom points |

**Resolution leans trimmed:** every rejected table caches a fold of data the
system already holds, and each buys an invalidation burden the system currently
has **zero** of. The expansive view's one fair point — admin telemetry blanks for
~6h after a restart — is a cosmetic gap on an admin-only panel, not a correctness
hole.

### Cheap additive wins both passes liked

- **Analytics indexes** — `idx_events_name_at`, `idx_events_user_name_at` so the
  admin rollups stay index-only as the event log grows. Pure
  `CREATE INDEX IF NOT EXISTS`, applied on boot.
- **`team_forms`** (optional) — persist only the *pre-tournament* form baseline so
  admin corrections survive restart and form decouples from the placeholder
  `fixtures.json`. The computed strip stays derived.

## Open questions (before any of it ships)

1. Backfill `result_events` from existing match scores on first deploy, or start
   history at the migration? *(Recommend: start at migration; the projection stays
   authoritative.)*
2. Wrap `SetResult` / `SetResultIfUnfinished` in a txn at the store, or compose
   append + update at the service layer? *(Decides whether the store grows a txn
   API.)*
3. Wire `SavePrediction` into the seed too, or accept that backfilled past-game
   rationale stays log-only? *(Cheap to include; the panel mostly cares about live
   reasoning.)*
4. Keep `confidence` as opaque TEXT, or normalize to an enum at the sanitize
   boundary so the panel can sort by it later?
5. Does the result audit need a gated admin TUI screen for launch, or is a
   DB-query artifact enough at first?

## Invariants preserved (both decisions)

- **Kickoff lock** — both new writes happen on already-post-kickoff/finalize
  paths; the lock stays entirely in `PlaceBet` + the sanctioned seed bypass.
- **Blind betting** — neither table stores picks visible pre-kickoff; `result_events`
  stores scores+actor, `ai_prediction` is admin-gated reasoning.
- **Pure scoring / edit-re-derives** — the scorer still reads `matches.score_a/b`;
  both new tables store *input*/free-text, never derived points, so nothing can
  drift from `scoring.Score`.
- **`ai` never imports `service`** — `ai_prediction` is written by the service/CLI,
  not the `ai` package; no new seam.
- **Single-writer DB** — both writes are tiny, on already-rare paths, on the
  existing connection; no max-conns bump, captured by the existing `.backup`.
